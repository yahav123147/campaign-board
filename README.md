# בורד הקמפיינים

שני מסלולים: **דף נחיתה בלחיצת כפתור** (סוכן ומבקר עם ציון לכל שלב, מכתובת אתר ועד דף בנוי), או **המועצה שעוזרת לך להשחיז רעיון גדול** (דיון של 8 מומחים, קופי, דף נחיתה, מודעות). שערי אישור אנושיים על מה שחשוב.

הבורד מציג את השם שההתקנה בחרה לעצמה דרך `ui.boardName` בפרופיל הלקוח. בלי בחירה הוא מציג "בורד הקמפיינים".

אפליקציית web מקומית ב-`127.0.0.1` שמפעילה סוכני Claude דרך מנוי קיים, מנהלת דיון אסטרטגי ושומרת כל ריצה בדיסק. המערכת אינה משתמשת במפתח Anthropic API ואינה אמורה להיות חשופה לרשת המקומית או לאינטרנט.

## תמיכת פלטפורמות

הזרימה המלאה נתמכת כרגע ב-macOS בלבד:

- שלב 5 מריץ קוד Next.js שנוצר על ידי מודל בתוך `sandbox-exec` של macOS. אין fallback לא מסונדבק, ולכן שלב 5 חסום ב-Linux וב-Windows.
- שלב 8 קורא את הטוקן של Meta מ-macOS Keychain בלבד. לכן אימות Meta, ובהמשך גם שלב 9 שתלוי באימות הזה, אינם מוכנים להפצה מלאה בפלטפורמות אחרות.
- מנגנון סגירת עץ תהליכים משתמש בקבוצות תהליכים של POSIX ותומך ב-macOS וב-Linux. הרצת סוכנים ב-Windows חסומה במכוון עד שיהיה מימוש מבוסס Job Object, כדי שתהליך שנקטע לא ישאיר צאצאים רצים ברקע.
- שלבים שאינם תלויים ב-sandbox או ב-Keychain עשויים לעבוד ב-Linux, אבל Linux אינו יעד הפצה מאומת בגרסה הזו.

ה-`doctor` בודק את המגבלות האלה. יכולת macOS-only שהופעלה במערכת אחרת היא חסימה, ויכולת שנשארה כבויה מוצגת כאזהרה בלבד.

## דרישות

- macOS עבור הזרימה המלאה
- Node.js 20.9 ומעלה ו-npm 9 ומעלה
- Python 3.10 ומעלה עבור כלי התמונות
- Claude Code (`claude`) מותקן ומחובר ב-OAuth של חשבון עם מנוי MAX פעיל
- Git, Chromium של Playwright ו-repository תקין של Next.js עבור שלב 5

כל הרצות Claude מבוצעות דרך `claude -p` ועל חשבון המנוי בלבד. אסור להגדיר `ANTHROPIC_API_KEY`, `CLAUDE_API_KEY`, Bedrock, Vertex או Foundry, ואין fallback ל-API בתשלום.

התחברות נכונה ל-Claude CLI:

```bash
claude auth login
claude auth status --json
```

פלט ה-auth מאמת OAuth של Anthropic, אבל אינו מספק שדה אמין לזיהוי רמת המנוי. לכן ה-`doctor` מזכיר לאמת ידנית שמדובר במנוי MAX.

## התקנה מקומית

שלוש פקודות. `setup.sh` מתקין את הכל (Node, Chromium, סביבת Python, תקני ברירת מחדל ופרופיל התחלתי) ומריץ בסוף את ה-doctor:

```bash
git clone <כתובת הריפו>
cd campaign-board
./setup.sh
```

את כתובת ה-clone לוקחים מכפתור **Code** הירוק בדף הריפו ב-GitHub.

מי שמעדיף ידנית, מתוך תיקיית הפרויקט:

```bash
npm ci
npx playwright install chromium

python3 -m venv "$HOME/.campaign-council-venv"
source "$HOME/.campaign-council-venv/bin/activate"
python3 -m pip install -r requirements-image-core.txt
```

יש להפעיל את ה-virtual environment בכל טרמינל שממנו מריצים את האפליקציה.

אם שלב 5 יופעל, יש לשכפל מראש repository נפרד של דפי הנחיתה ולהתקין גם בו את התלויות לפי קובץ ה-lock שלו. ה-`doctor` אינו מתקין תלויות ואינו משנה את ה-repository.

## תקני קראפט (הסקילים)

לשלב 5 (בניית דפים) מצורף גם **סקיל העיצוב המלא** ב-`vendor/landing-skill/` (תקן Dark Premium RTL, ספריית סקציות, אנימציות, ושער ה-QA). התקנה לריפו הדפים לפי `vendor/landing-skill/INSTALL.md`.

איכות התוצרים תלויה בתקנים שהבורד שופט לפיהם. בלי תקן, הכותבים והמבקרים שופטים לפי טעם, והתוצאה בינונית. החבילה מגיעה עם שני תקני ברירת מחדל מלאים:

- `config/standards/copy-standard.default.md`: מתודולוגיית דפי מכירה בעברית (פרוטוקול 24 השלבים) + כללי קול, שפה ואנלוגיות.
- `config/standards/ads-standard.default.md`: מתודולוגיית קופי מודעות Meta + קורפוס דוגמאות + תבנית UTM מלאה.
- `config/standards/creative-standard.default.md`: תקן הפקת קריאייטיבים לשלב 7.5, מבנה 4 שכבות, פריסה, וחוק "הקופי לתמונה נכתב מחדש, לא נגזר". מופעל דרך `creative.standardPath` בפרופיל.
- **מודל הסוכנים:** `CAMPAIGN_COUNCIL_AGENT_MODEL` ב-`.env.local` קובע את המודל לכל תור סוכן. הסוכנים רצים עם הגדרות מושתקות, ולכן בלי המשתנה הזה הם נופלים לברירת המחדל של ה-CLI ולא למודל שהגדרתם ב-Claude. בדקו זמינות במנוי לפני: `claude -p --model <id> "hi"`.
- **בחירת מצב קריאייטיב (שלב 7.5):** בריצה ראשונה השער עוצר ושואל את הלקוח: טקסט על התמונה האמיתית (חינם) או וריאציית AI מהתמונה דרך images/edits של OpenAI (קרדיטים; הפנים מצוירות מחדש רק בבחירה מפורשת). באותו מסך אפשר להעלות תמונת פרזנטור מהדפדפן; ההעלאה עוברת ניקוי EXIF/GPS אוטומטי. תיקיית ברירת מחדל: `~/.config/campaign-council/presenter-photos/<tenant-id>` (סקופ פר לקוח, למניעת זליגת תמונות בין פרופילים) כשלא הוגדרה `creative.presenterPhotosDir`.

התקנה: העתיקו את שני הקבצים למיקום פרטי מחוץ ל-repository (למשל `~/.config/campaign-council/`), והצביעו עליהם בפרופיל הלקוח דרך `copy.standardPath` ו-`copy.adsStandardPath` (נתיבים מוחלטים). התקנים נקראים מהדיסק בכל ריצה, כך שאפשר לערוך אותם בכל רגע בלי להפעיל מחדש. מותר ומומלץ להתאים אותם לקול של הלקוח.

אחרי כל שכתוב קופי רצה **ביקורת ציות לסקיל**: סוכן בודק את התוצר שורה מול כלל (ובריצת משוב, שהשינוי היחיד הוא מה שהמשוב ביקש). כשל כפול מסומן בראש התוצר, ובמצב אקספרס השער נעצר לאדם.

## שלב 7.5: הפקת קריאייטיבים (אופציונלי)

אחרי אישור המודעות, הבורד יכול להפיק את התמונות עצמן: סוכן ארט מתרגם כל Creative brief לתוכנית, רקע מיוצר דרך OpenAI Images (במפתח של הלקוח), והעברית מונחת מעל ב-Pillow עם פונט Heebo, כי מנועי תמונה מרסקים אותיות עבריות. כל תמונה עוברת בדיקות איכות וגיליון אישור אנושי.

הפעלה בפרופיל: `policies.capabilities.creativeImageGen: true` + `creative.openaiKeychainService` (שם שירות ב-macOS Keychain שמחזיק מפתח OpenAI API של הלקוח: `security add-generic-password -s <service> -a openai -w <key>`). המפתח נקרא רק על ידי האפליקציה ולעולם לא נחשף לסוכן.

**פנים אמיתיות בלבד:** פנים של פרזנטור לעולם לא מג'ונרטות. אם הלקוח רוצה מודעות עם הפנים שלו, הוא שם 3-5 תמונות אמיתיות בתיקייה ומגדיר `creative.presenterPhotosDir`; בלי תיקייה, כל הקריאייטיבים נבנים בלי בני אדם. כשהיכולת כבויה, השלב מדלג עם הסבר והצנרת ממשיכה.

## שערים וקצב

- `gates.policy` בפרופיל: `"full"` (ברירת מחדל, כל שער מאושר ידנית) או `"express"`, שבו הבורד מאשר לבד את השערים השגרתיים ועוצר לאדם רק ב: סוף הקופי (4e), גיליון הנכסים (5.2), הדף אחרי QA (5.4), המודעות (7) ושלבי Meta (8-9).
- שער 7.5 (קריאייטיבים) אנושי תמיד כשהיכולת פעילה: אין תמונה שיוצאת בלי עין אנושית.
- `discussion.rounds` בפרופיל: 1, 2 או 3 סבבי דיון אסטרטגיה. ברירת המחדל 2 (עמדות + עימותים; הסינתזה מתכנסת). בריף מלא ומפורט מסתדר עם 1; מי שרוצה את הדיון המקורי המלא יגדיר 3.

## פרופיל לקוח וסביבה

1. העתיקו את `config/client-profile.example.json` לקובץ פרטי מחוץ ל-repository והגבילו אותו להרשאות של המשתמש הנוכחי בלבד.
2. מלאו רק עובדות מאומתות והרשאות שהלקוח אישר במפורש.
3. העתיקו את `.env.example` ל-`.env.local` והגדירו ב-`CAMPAIGN_COUNCIL_CLIENT_PROFILE` נתיב מוחלט. אין להשתמש ב-`~` או ב-`$HOME`, כי ערכי dotenv אינם מורחבים על ידי shell.
4. כברירת מחדל הריצות נשמרות בתיקיית application data פרטית של מערכת ההפעלה. אפשר להגדיר בסיס חלופי עם `CAMPAIGN_COUNCIL_DATA_DIR`.
5. אם שלב 5 פעיל, הגדירו `LANDING_PAGES_DIR` לאותו נתיב שמופיע ב-`landing.workspacePath` בפרופיל.
6. לשלב 5 הגדירו בפרופיל גם `landing.designStandardPath` ו-`landing.qaScriptPath`. שניהם נתיבים יחסיים בתוך repository דפי הנחיתה, לא נתיבים לתיקיית הבית.

כל נתיב אחסון שמגדירים חייב להיות נתיב מוחלט לתיקיית משנה ייעודית. המערכת
מסרבת להשתמש ב-root של מערכת הקבצים, בתיקיית הבית עצמה, ב-root של הפרויקט,
בתיקיית temp רחבה או בתיקייה ישירה תחת root. ברירת המחדל המערכתית היא הבחירה
הבטוחה כאשר אין צורך להעביר את האחסון למיקום אחר.

את `PREVIEW_PORT` יש לקבוע ב-`.env.local` לפני `npm run build`, ולהשאיר באותו ערך
גם בזמן `npm run start`. מדיניות ה-CSP של הגרסה הבנויה מאשרת רק את origin התצוגה
המדויק הזה. שינוי הפורט מחייב build חדש לפני ההפעלה.

דוגמה ליצירת עותק פרטי ב-macOS:

```bash
mkdir -p "$HOME/.config/campaign-council"
chmod 700 "$HOME/.config/campaign-council"
cp -n config/client-profile.example.json "$HOME/.config/campaign-council/client-profile.json"
chmod 600 "$HOME/.config/campaign-council/client-profile.json"
cp -n .env.example .env.local
chmod 600 .env.local
```

לאחר מכן יש לערוך את שני הקבצים ולהציב ב-`.env.local` את הנתיב המוחלט בפועל.

לבדיקות ממשק בלבד, בלי הפקת דפים ובלי גישה ל-Meta, אפשר להגדיר:

```dotenv
CAMPAIGN_COUNCIL_USE_DEVELOPMENT_PROFILE=1
```

אין לשלב development profile עם פרופיל לקוח אמיתי.

### תקן הקופי של שלב 4

`copy.standardPath` הוא נתיב מוחלט לקובץ markdown יחיד עם כללי הכתיבה שהלקוח
עובד לפיהם. הוא אופציונלי. כשהוא מוגדר, הקובץ נקרא מהדיסק בזמן ריצה ונכנס
לשלושת השלבים של שלב 4: הכותב מקבל אותו לפני הטיוטה, המבקרים שופטים לפיו,
והכותב מקבל אותו שוב בשכתוב. כך הכללים לא נסחפים מהפרומפט, בדיוק כמו תקן
העיצוב של שלב 5.

הקריאה fail-closed: קובץ חסר, symlink, קובץ ריק או קובץ מעל 256KB עוצרים את
השלב במקום להריץ אותו בלי תקן. כשהשדה לא מוגדר, לא מתווסף כלום לפרומפט
וההתנהגות זהה לקודמת.

### תבניות סוגי הדף

לכל סוג דף שאינו דף מכירה (ליד פרימיום, וובינר, סקוויז, אפסייל) יש קובץ תבנית
נפרד שקובע מבנה מחייב, מה אסור בסוג הזה, ואיזה נכסים נדרשים. ברירות המחדל
הנקיות יושבות ב-`config/standards/page-types/<סוג>.default.md`, ו-`setup.sh`
מעתיק אותן ל-`<CONFIG_DIR>/page-types/<סוג>.md` באותה לוגיקה של "לא דורסים
קובץ קיים" שמשמשת את שאר התקנים.

**כברירת מחדל אין צורך להגדיר כלום בפרופיל.** התיקייה נגזרת אוטומטית מהנתיב
של קובץ הפרופיל שנטען (`<dirname(CAMPAIGN_COUNCIL_CLIENT_PROFILE)>/page-types`),
כלומר תיקיית `page-types` ליד קובץ הפרופיל עצמו. `copy.pageTypesDir` בפרופיל
הוא שדה אופציונלי, ונדרש רק כשהתבניות יושבות בתיקייה אחרת (נתיב מוחלט).

תבנית חסרה לא חוסמת ריצה: השלב הרלוונטי ממשיך על ההוראות שבקוד בלבד, אבל
`npm run doctor` בודק, לכל סוג שאינו דף מכירה, שקיים קובץ תבנית קריא, ומדווח
אזהרה עם פעולה ברורה כשמשהו חסר.

### תנאי סף לשלב 5

שלב 5 מופעל רק כאשר `policies.capabilities.landingPageBuild` הוא `true` וכל השדות הבאים קיימים:

- `landing.workspacePath`: נתיב מוחלט ל-root של Git repository אמיתי, לא symlink
- `landing.designStandardPath`: קובץ יחסי בתוך אותו repository
- `landing.qaScriptPath`: קובץ יחסי בתוך אותו repository
- `LANDING_PAGES_DIR`: אותו נתיב מוחלט בדיוק כמו `landing.workspacePath`

ה-repository צריך לכלול `package.json`, תיקיות `src/app` ו-`public`, metadata של Git, התקנת Next.js מקומית והרשאות קריאה וכתיבה. העבודה מתבצעת ב-worktree מבודד מ-HEAD שבוצע לו commit, ולכן שינויים מקומיים שלא בוצע להם commit אינם נכנסים לבנייה. לאחר ששער ה-QA והתצוגה אושרו, המערכת מאמתת שוב את חותמות המקור והנכסים ושומרת commit מבוקר בענף `campaign-council-<run-id>`. היא אינה מבצעת push או merge.

סקריפט ה-QA הוא חוזה fail-closed: עליו להחזיר קוד יציאה `0`, שורת `PASS <width>px`
אחת לכל אחד מהרוחבים `320, 360, 390, 430, 768, 1280`, ולבסוף שורת
`RESULT: PASS` יחידה. timeout, crash, פלט חסר, רוחב חסר או `FAIL` משאירים את 5.4
פתוח למשוב וחוסמים commit. קבלת ה-QA נשמרת עם hash של דוח הבדיקה וקשורה לחותמות
המקור והנכסים המדויקות שנבדקו.

### תנאי סף לשלבים 8 ו-9

שלב 8 הוא אימות read-only מול Meta. הוא מופעל רק כאשר `policies.capabilities.metaPixelRead` הוא `true` וכל השדות הבאים קיימים:

- `meta.accountId`, בפורמט `act_` ואחריו ספרות
- `meta.pixelId`
- `meta.customConversionId`, חובה ולא שדה אופציונלי כאשר שלב 8 פעיל
- `meta.domain`, hostname בלבד ללא scheme, path או port
- `meta.tokenKeychainService`, שם פריט Generic Password ב-macOS Keychain

ברירת המחדל היא Graph API `v26.0`. כאשר Meta מחייבת שדרוג גרסה אפשר לעדכן רק את
`META_GRAPH_API_VERSION` ב-`.env.local`, בפורמט `vNN.0`. ה-host נשאר מקובע ל-`graph.facebook.com`.

הטוקן עצמו לעולם אינו נשמר בפרופיל או ב-`.env.local`. אפשר ליצור או לעדכן אותו ב-macOS כך, כאשר הערך של `-s` זהה בדיוק ל-`meta.tokenKeychainService`:

```bash
/usr/bin/security add-generic-password -U \
  -a "$USER" \
  -s "campaign-council-meta-client" \
  -w
```

האפשרות `-w` נשארת אחרונה כדי שהפקודה תבקש את הסוד באופן אינטראקטיבי. אין להדביק טוקן בשורת הפקודה, בקובץ dotenv או ב-Git.

שלב 9 דורש בנוסף את `policies.capabilities.metaCampaignCreatePaused`, את `meta.pageId`, את `meta.instagramActorId` ואת `landing.publicBaseUrl`. בגרסה הזו הוא מפיק תוכנית בלבד ואינו מפרסם קמפיין.

## בדיקת מוכנות לקריאה בלבד

לאחר ההתקנה הריצו:

```bash
npm run doctor
```

מומלץ להריץ את הבדיקה כאשר האפליקציה ושרת התצוגה המקומי עצורים, כדי שבדיקת הפורטים תשקף מצב התחלה נקי.

ה-doctor בודק גרסאות Node/npm/Python, חיבור OAuth של Claude, היעדר משתני API אסורים, Chromium של Playwright, מודולי תמונה, תיקיית נתונים פרטית, פורטים מקומיים, פרופיל לקוח, sandbox מקומי, סביבת דפי הנחיתה וקיום פריט ה-Keychain המוגדר. בדיקת Keychain אינה מבקשת ואינה מדפיסה את הסוד. ה-doctor אינו מתקין, יוצר או משנה קבצים והרשאות.

קוד יציאה `0` אומר שאין חסימות. אזהרות יכולות להישאר כאשר יכולות אופציונליות מושבתות בכוונה. קוד יציאה `1` אומר שצריך לטפל לפחות בחסימה אחת לפני הרצה אמיתית.

## הרצה

```bash
source "$HOME/.campaign-council-venv/bin/activate"
```

## אימות וחילוץ חבילת לקוח

כל חבילה מגיעה כארכיון וכקובץ checksum תואם. לפני החילוץ, הניחו את שניהם באותה
תיקייה ואמתו שהארכיון לא השתנה בדרך:

```bash
shasum -a 256 -c campaign-council-client-*.sha256
tar -xzf campaign-council-client-*.tar.gz
cd campaign-council
```

שם הארכיון כולל את גרסת החבילה ואת 12 התווים הראשונים של commit המקור, כדי
שאפשר יהיה לזהות במדויק איזו גרסה מותקנת אצל לקוח.

## הכנת עותק ללקוח, למתחזקי ההפצה

הפצה ללקוח צריכה להיעשות מארכיון נקי ולא מהעתקה של תיקיית העבודה או של היסטוריית
Git. לאחר שכל השינויים עברו בדיקות ובוצע להם commit, הריצו:

```bash
npm run package:client
```

הפקודה מסרבת לעבוד מחוץ ל-root של ה-repository או על worktree מלוכלך. היא יוצרת
archive וקובץ SHA-256 תחת `dist/`, ומוודאת שהארכיון כולל את קבצי ההתקנה והדוגמאות
אך אינו כולל `.git`, קבצי `.env`, ריצות, פרופיל לקוח אמיתי, מפתחות, מסמכי תכנון
פנימיים או הוראות agent מקומיות. Symlinks ו-submodules חסומים כדי שהחילוץ יהיה
עצמאי וצפוי. את קובץ פרופיל הלקוח האמיתי יוצרים אצל הלקוח מחוץ ל-repository, לפי
הדוגמה שבארכיון.

## מבנה

- `agents/`: הגדרות ופרומפטים של הסוכנים
- `orchestrator/`: מנוע הדיון ושלבי הביצוע
- `app/`: מסכים ונתיבי API של Next.js
- `components/`: רכיבי React
- `config/`: סכמת פרופיל לקוח ודוגמה בטוחה
- `lib/`: עזרים ושמירת ריצות
- `scripts/`: כלי QA, תמונות ו-doctor
- `types/`: טיפוסי TypeScript
- `runs/`: אחסון legacy בלבד. ריצות חדשות נשמרות בתיקיית application data הפרטית

## תיעוד למפתחים

המפרטים ותוכניות היישום נשמרים מקומית בתיקיית `docs/` על מחשב הפיתוח. התיקייה
אינה במעקב git ואינה נכללת בחבילת הלקוח.
